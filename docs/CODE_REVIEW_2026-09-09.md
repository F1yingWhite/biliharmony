## 优先修复的问题

P1 表示会破坏功能正确性或资源生命周期，P2 表示体验、恢复能力和性能风险；不是生产事故等级。

### 1. P1：楼中楼切换后混入上一条评论的回复

位置：`pages/VideoDetail.ets:1910` 的 `openReplyThread`、`:1959` 的 `loadThreadReplies`。

打开根评论 A，首批请求未结束时关闭面板，再打开 B。B 改写当前根评论和预览列表，但全局 `threadLoading` 拦住 B 的请求。A 返回后只检查页面是否销毁，直接合并到 B 的列表，并覆盖 B 的分页游标。复现得到当前根为 200，列表同时包含根 200 和根 100 的回复，API 只调用一次。

应以视频/动态 ID、评论类型、根评论 ID 和请求代次共同确认归属。切根必须使旧请求失效，并发起当前根的首批请求；旧请求的 `finally` 也不能复位新请求状态。验收覆盖慢请求下 A→B、关闭重开及快速切换。

`pages/DynamicDetail.ets:355`、`pages/BangumiDetail.ets:309` 存在同类缺少根评论归属校验的代码，尚未分别做设备复现。

### 2. P1：AVSession 在释放后重新激活，正常释放也没有销毁会话

位置：`components/player/PlayerAvSessionHelper.ets:30`、`:95`；调用方 `PlayerView.ets:534`。

`ensure()` 等待创建期间，页面调用 `release()` 并丢弃 helper；创建随后完成，旧 helper 仍会激活会话并保存引用。复现中 release 后 `active` 又变为 true。正常释放只调用 `deactivate()`，没有 `destroy()`；创建过程后续步骤失败时也没有清理已创建的会话。

本机 Release SDK 的 `@ohos.multimedia.avsession.d.ts:1694–1726` 明确区分停止接收控制指令和销毁服务端资源。应统一资源所有者，在每个异步阶段校验代次；迟到的创建结果、部分创建失败和最终退出都要销毁，释放操作须可重复调用。设备上媒体中心残留和资源累计程度待测。

### 3. P1：直播初始化出错时，备用线路重试被丢弃

位置：`components/live/LivePlayerView.ets:99` 的 `initPlayer`、`:166` 的 `handleError`。

`setMediaSource()` 尚未完成时收到 error，错误处理释放播放器并调用 `initPlayer()` 切备用 URL，但 `playerCreating` 仍为 true，入口直接返回。外层 finally 清除标记后没有补建。复现中存在可用备用 URL，但播放器为空且只创建过一次。

应把“下一次期望创建”放入统一生命周期流程，保证创建结束后处理待办换源，错误分支也需校验代次。验收分别覆盖创建期错误、播放期错误和错误处理期间再次换源。

### 4. P1：刷新二维码后，旧轮询可使新二维码立即过期

位置：`pages/Login.ets:78` 的 `requestCode`、`:132` 的 `poll`。

停止定时器不会取消已发出的轮询。旧二维码的过期响应返回时仍能停止新轮询并更新新页面。复现明确得到新二维码被旧 `86038` 响应标记过期；旧成功响应也缺少归属检查。

二维码请求和轮询应共享登录尝试代次，切换方式、刷新和页面退出时失效。不能只增加 busy 标记，否则会把用户刷新请求一起丢掉。

### 5. P1：下载任务移除后，全局下载状态可能永久占用

位置：`services/media/VideoDownloadService.ets:20`、`:60`。

只订阅 `progress/complete/fail`，没有处理 `remove`。Release SDK 的 `@ohos.request.d.ts:731` 提供独立移除事件。复现只触发 remove 时，Promise 一直未结束，`active` 一直为 true，后续下载被“已有下载任务”拦截。

需要统一完成、失败、取消的终态及监听清理。取消应结束整项下载，不能误当作 CDN 失败继续下载备用地址。系统通知栏/任务管理实际触发顺序待验证。

### 6. P1：登录状态变化时，首页刷新可能丢失

位置：`views/HomeView.ets:93`、`:159`。

推荐请求在途时，登录状态触发的 reset 被 `recFetching` 直接丢弃；旧请求返回空时，又把 `recHasMore` 设为 false，原列表保留，新账户的 reset 没有再执行。复现确认了这个顺序。

网络层已经有账户代次隔离，不能因此声称所有旧账户响应都会泄露给新账户；本问题在页面层的刷新调度和显示状态。应让 reset 取代旧分页请求，按当前账户重新加载，并区分失败、空列表和末页。

### 7. P2：清空稍后再看后，旧加载结果又显示回来

位置：`pages/library/WatchLaterPage.ets:53`、`:109`。

`loading` 和 `actionBusy` 各自运行。清空成功重置数据源后，之前发出的列表请求仍会写回旧列表。复现中清空后数量从 0 回到 1；这是 UI 状态回滚，不代表服务端删除失败。

写操作成功应使旧读取失效，再由明确的数据版本或重新查询更新页面。单条删除也应覆盖相同的并发边界。

### 8. P2：动态分类的选中项与实际数据类型不一致

位置：`views/DynamicView.ets:1227`、`:1256`、`:1559`。

点击或滑动先更新 `dynTab`，但 `changeDynType` 在 `feedLoading` 时返回，保留旧 `dynType`。复现中标签已选视频，查询类型仍为全部。多个 Tab 又共用同一个数据源，会放大这种错位。

应使所选分类成为查询的唯一输入；加载中切换也要记录并落实最新选择。验收包含首屏加载、触底分页时连续切换。

### 9. P2：直播表情解码迟到，释放后重新进入缓存

位置：`components/live/LiveDanmakuRenderer.ets:144`、`:228`。

`release()` 只释放当前缓存，清空 loading 集合不会终止请求。异步解码返回后仍执行 `emoteCache.set()`。复现中 release 后缓存重新出现一个 PixelMap，未显式 release。

应给渲染器和解码结果添加生命周期归属，过期 PixelMap 立即释放。同时限制缓存总量；当前按 URL 存储，没有会话内淘汰机制。持续增长的实际内存量仍需采样。

## 重构顺序

1. **先建立请求归属规则。** 复用已有 `RequestEpoch`、`AuthSession` 思路，抽出带查询标识的分页状态。reset、切账户、切分类和切评论根都应使旧结果失效；错误不能伪装成空页。优先迁移楼中楼、首页、动态与稍后再看。
2. **统一媒体资源所有者。** 分开处理播放源调度、AVPlayer 生命周期和 AVSession/后台任务生命周期，让退出、换源、失败都能收敛到可验证终态。保留已有 `PlaybackSourceCoordinator`，避免继续靠新增布尔标记和定时等待补洞。
3. **建立下载任务模型。** 保存任务 ID、状态与目标，处理取消/移除和进程重建；完成媒体下载后复制到用户选择 URI 的流程也需恢复策略。当前只有进程内全局锁和单次 Promise。
4. **再拆页面。** `PlayerView` 约 3682 行、`VideoDetail` 约 3069 行；先抽出上述状态所有者，再按稳定职责拆展示组件，避免只把文件切碎但仍共享可变状态。
5. **最后统一交互与视觉规范。** 面板列宽、行高、触控区域、错误态、开关、功能可用状态统一处理。优先修真实入口和布局适配，再评估装饰效果。

补充加固：`services/auth/UserStore.ets:34/87/97` 同时向 PersistentStorage 与 Preferences 保存原始 Cookie/token 字符串，未在应用代码中使用凭据保险箱或显式加密。应设计单一凭据存储与迁移清理流程；这是静态加固建议，不能据此声称沙箱外可读取或已发生凭据泄露。本轮未读取真实凭据。
